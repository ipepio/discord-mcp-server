# 0001 — Stable feature ownership and NestJS composition

- Status: Accepted baseline
- Scope: Architecture
- Acceptance basis: Owner requested a NestJS guidance template retaining the source repository's
  way of working: "la arquitectura y patrones serán siempre las mismas" and
  "Quiero qyue los agentes se adapten a trabajar a mi forma, no yo al agente".

## Context

The integration source separates handlers, commands, gateways, wire/domain models and mappers.
Its PMS/POS-specific package names are not universal business concepts. A fresh project needs the
same responsibilities without inherited industry assumptions or agent-selected architecture drift.

## Decision

Use a feature-based NestJS shell with thin transport adapters, commands/queries, framework-free domain,
explicit persistence/external-system contracts and composition modules. Define ownership through
[the placement guide](../architecture/structure.md) and [feature patterns](../architecture/features.md).
Create only layers needed by actual behavior; a monorepo and separate published packages are not
required for a standalone application. Shared code is technical infrastructure, not displaced business.

## Consequences

Agents get predictable placement and dependency rules. Cross-feature contracts must be intentional.
No ORM, bus, generic CRUD framework or alternative transport is introduced by preference. A genuine
exception requires owner acceptance, not just an agent-authored record.

This record documents the baseline; it does not claim executable enforcement. Future authorized setup
must implement and negatively test import boundaries as described in [testing](../architecture/testing.md).
Business specifications and tests remain project-specific. No application is generated by this ADR.
